# pycode: класс — спецификация

Дата: 2026-10-30. Статус: черновик на ревью.

## Цель

Превратить pycode из «IDE с общим экраном» в инструмент для занятий
репетитора с группой. Нужны:

- роли и права доступа вплоть до отдельных папок учеников;
- задания с автопроверкой, тесты которых ученик не видит;
- отладчик;
- бинарные файлы, просмотр PDF/PPTX и режим презентации;
- Markdown и простой фронтенд (HTML/CSS/JS) с превью;
- доска в стиле Miro.

## Принципы

1. **Сервер минимален.** Он выдаёт коды и роли, выбирает исполняющего
   обязанности владельца, передаёт сигналинг и relay. Содержимое проекта
   он не видит и не хранит. Всё остальное делают клиенты.
2. **Права проверяет получатель.** Это продолжение текущей модели:
   изменения от viewer уже отбрасываются.
3. **Проще, а не универсальнее.** Где есть готовая библиотека, берём её.
   Где есть два пути, выбираем тот, в котором меньше кода.

## 1. Модель проекта

Сейчас проект — это один Y.Doc. Он становится набором документов, и у
каждого свои права:

| docId | Содержимое | Чтение | Запись |
|---|---|---|---|
| `structure` | `files`, `dirs`, `roles`, `folders`, `packages`, `state` (`frozen`, `presentation`) | все | admin |
| `runtime` | `terminal`, `run`, `debug` | все | write |
| `board` | элементы и картинки доски | все | write |
| `f:<id>` | `Y.Text` одного текстового файла | по правилам §2 | по правилам §2 |

`structure.files` хранит запись `path → FileMeta`:

```ts
{ id: string; kind: "text" | "binary"; size: number; hash?: string; mime?: string; protected?: true; hidden?: true }
```

- **Переименование** меняет только ключ `path`, а `id` и документ
  содержимого остаются прежними. Копирование `Y.Text`
  (`renamePath` сейчас) уходит.
- **Хранение:** `y-indexeddb`, по одной базе на документ:
  `pycode:<docId>`. Бинарные файлы лежат в отдельной базе
  `pycode:blobs`, ключ — `sha256`.
- **Сброс** очищает все базы.
- **Гость** держит документы только в памяти и теряет их при выходе, как
  сейчас.
- **Миграция:** при первом запуске старый `python-coder:project`
  переносится в новые документы, после чего старая база удаляется.

## 2. Роли и доступ

### Уровни и роли

- Уровни: `read` < `write` < `admin`. Владелец (`owner`) — это admin с
  правом сброса и завершения сессии.
- Встроенные роли: `read`, `write`, `admin`.
- Кастомная роль (например `ivan`) создаётся с базовым уровнем `read`
  или `write`. Этот уровень действует для публичных файлов. В папках
  своей роли кастомная роль всегда может читать и писать.
- Папке можно назначить одну роль: `structure.folders: path → roleName`.
- Вложенные папки с ролями: чтобы видеть и открывать внутреннюю папку,
  нужен доступ ко всем папкам с ролями на пути к ней. Если у внешней и
  внутренней папок роли разные, внутреннюю видит только admin.
- Роли хранятся в проекте (`structure.roles: name → {level}`), а значит
  переживают сессии и попадают в архив.
- Удалить роль из проекта можно. Папки с удалённой ролью остаются
  закрытыми и доступны только admin.

### Права на файл

Функция `access(member, path)` возвращает `none`, `read` или `write`.
Проверки 1–4 идут по порядку, первая сработавшая даёт результат. Правило
5 затем ограничивает этот результат:

1. admin или owner → `write`.
2. Файл скрыт (`hidden`) → `none`.
3. Хотя бы одна папка с ролью на пути принадлежит чужой роли → `none`.
   Если на пути есть папки с ролями и все они своей роли → `write`.
4. Иначе (публичный файл) → базовый уровень участника. Если файл
   защищён (`protected`), не выше `read`.
5. Если включена заморозка, итог не выше `read` (для всех, кроме admin).

Что разрешено каждому уровню:

| Действие | read | write | admin |
|---|---|---|---|
| Видеть файл в дереве | если `access ≠ none` | так же | всё |
| Редактировать | — | если `access = write` | всё |
| Запускать, отлаживать, вводить в консоль, рисовать на доске | — | ✓ (кроме заморозки) | ✓ |
| Создавать, удалять, переименовывать файлы и папки, перетаскивать | — | — | ✓ |
| Защищать файлы, скрывать и показывать тесты, назначать роли папкам | — | — | ✓ |
| Пакеты, заморозка, презентация, роли и ссылки | — | — | ✓ |
| Сброс проекта | — | — | только owner |

- **Защищённый файл.** В контекстном меню admin есть «Защитить» и «Снять
  защиту», в дереве показывается иконка замка. Запускать защищённый
  файл может любой, у кого есть право запуска.
- **Тест.** `*.test.py` при создании получает `hidden`. Admin может
  открыть его ученикам переключателем «Показать ученикам».
- **Чего не скрываем.** Пути всех файлов (`structure`) видны любому
  участнику через DevTools. В интерфейсе недоступные файлы спрятаны, а
  их содержимое к участнику не попадает вообще.

### Заморозка

Admin нажимает «Заморозить» (иконка снежинки) в шапке, и выставляется
`structure.state.frozen = true`. Все, кроме admin, переходят в режим
чтения:

- редактор только для чтения;
- запуск и ввод в консоль недоступны;
- доска переходит в режим просмотра.

Анимация:

- **Включение:** иней нарастает от краёв экрана примерно за 1,2 с. Это
  SVG `feTurbulence` под радиальной маской, бело-голубой тон и
  `backdrop-blur` по краям.
- **Пока заморозка активна:** по краям остаётся тонкая морозная
  виньетка с `pointer-events: none`.
- **Выключение:** иней «тает» (прозрачность и blur примерно за 0,6 с).
- **`prefers-reduced-motion`:** анимации нет, только виньетка.

Анимацию видят все.

### `.pycode.env`

Файл в корне архива описывает все права. Формат построчный, путь всегда
идёт последним и может содержать пробелы:

```
# pycode access rules
role ivan write
folder ivan students/ivan
protected task.py
hidden task.test.py
```

- **Экспорт** создаёт файл, если есть хоть одно правило.
- **Импорт** читает и применяет правила, файлом в проекте он не
  становится.
- **Имя зарезервировано:** в корне нельзя создать файл с таким именем или
  переименовать в него.

## 3. Сессия

### Ссылки и коды

- У каждой роли свой код и своя ссылка: встроенные `read`, `write`,
  `admin` и каждая кастомная роль.
- Роль участника определяется кодом, по которому он вошёл. Владелец
  (по cookie) всегда остаётся owner.
- Окно «Поделиться» показывает список ролей: ссылка, код, кнопка
  «Скопировать». Там же «Добавить роль» (имя и уровень) и галочка
  «Спрашивать имя».
- Роли можно создавать и до начала сессии. Коды появляются после её
  старта.
- Режимы `read_only`/`read_write` убираются.

### Имя

- Если при старте отмечено «Спрашивать имя», то при первом входе в эту
  сессию участник видит окно «Как вас зовут?».
- Имя хранится в `localStorage` под ключом `pycode:name:<code>`. Поле
  заполняется последним введённым именем.
- Имя публикуется в awareness.
- Без галочки используются сгенерированные имена, как сейчас.

### Замена владельца

- Сервер следит за `room.owner`. Если владелец онлайн, это он. Иначе —
  admin, который вошёл раньше всех из тех, кто сейчас онлайн. Если таких
  нет, `0`.
- При каждой смене сервер рассылает `{"type":"owner","peer":N}`.
- Исполняющий обязанности получает права owner (сброс, цель для
  «Следовать»). Завершить сессию может только настоящий владелец.
- Когда настоящий владелец возвращается, сервер снова отдаёт ему роль, и
  временный владелец снова становится обычным admin. Документ владельца
  догоняет изменения через обычную синхронизацию Yjs.

### Следовать

- Кнопка «Следовать» (иконка глаза) в шапке сессии.
  - Первое нажатие — следовать за текущим owner.
  - Повторное нажатие во время слежения открывает меню: участники (имя и
    цвет) и «Перестать следовать».
- Каждый участник публикует в awareness `view: { tab, file, scrollTop }`
  и `boardView: { scrollX, scrollY, zoom }`. Тот, кто следует, применяет
  их у себя.
- Если пользователь сам откроет другой файл или вкладку, слежение
  прекращается. Правка кода слежение не прекращает.

### Подписи курсоров

- По умолчанию подписей нет, только цвет.
- Тумблер «Имена у курсоров» в футере рядом с темой. Состояние хранится в
  `localStorage`.
- Тумблер действует и на курсоры на доске.

### Синхронизация

- К каждому sync-сообщению добавляется `docId`: `[MSG_SYNC][docId][y-sync payload]`.
- **При установке связи** каждая сторона отправляет sync step1 для своих
  документов. Ответ step2 и последующие обновления уходят только тем,
  кому `access ≥ read`.
- **Получатель** применяет изменение, только если у отправителя есть
  `write` для этого документа. Права считаются по собственному
  `structure` получателя.
- **Новый файл в `structure`** или новый доступ: получатель отправляет
  step1 для этого документа. Это же чинит ситуацию, когда изменения
  пришли не в том порядке.
- **Следствие:** документы с правом записи только у admin (`structure`,
  защищённые, скрытые) новичок получает только от admin или owner. Пока
  ни одного из них нет в сети, новый участник не загрузит проект. Так
  же сейчас: проект живёт у владельца.

## 4. Бинарные файлы и перетаскивание

- **Текст или бинарный.** Файл текстовый, если у него знакомое
  расширение (`py md txt json yaml yml toml csv html htm css js mjs xml
  svg ini`) или он без ошибок декодируется как UTF-8 и не содержит NUL.
  Остальное — бинарные файлы: `FileMeta.kind = "binary"`, `hash`,
  `mime`, а байты в `pycode:blobs`.
- **Лимит: 64 МБ на проект.** Сумма бинарных файлов, текстов и картинок
  доски. Если добавление превышает лимит, ничего не добавляется и
  показывается toast.
- **Передача по запросу.** `ensureBlob(hash)` вызывается при открытии
  файла, перед запуском (для всех доступных бинарных файлов) и при
  экспорте. Запрос `BLOB_GET {hash, part}` уходит текущему owner, а если
  у него нет файла — следующему участнику. Ответ `BLOB_PART` идёт
  кусками по 1 МБ через тот же канал. Отдаём файл только тем, у кого
  `access ≠ none`. После сборки сверяем `sha256`.
- **Перетаскивание (только admin).** Файлы перетаскивают на любое место
  окна.
  - Панель файлов раскрывается, поверх неё появляется слой с
    анимированной пунктирной рамкой и подписью «Отпустите, чтобы
    добавить».
  - Папка под курсором подсвечивается и становится целевой, иначе файлы
    попадают в корень.
  - Папки загружаются рекурсивно (`webkitGetAsEntry`).
  - Если имя занято, добавляется суффикс: `name (2).ext`.
  - Новые строки в дереве на мгновение подсвечиваются.
  - Не-admin слоя не видит, а браузер при сбросе файла ничего не
    открывает (`preventDefault`).
- **Zip.** Импорт определяет бинарные файлы тем же способом, а не
  превращает их в «нечитаемый текст» как сейчас. Экспорт включает
  бинарные файлы и `.pycode.env`.
- **Просмотр бинарных файлов.**
  - Картинки показываются через `<img>`.
  - PDF и PPTX — см. §5.
  - Остальное показывается карточкой: имя, размер, «Скачать».

## 5. Просмотр: Markdown, PDF, PPTX, презентация

- **Markdown.** В шапке редактора переключатель «Код | Рядом |
  Просмотр». По умолчанию «Рядом», выбор хранится в `localStorage`.
  - Превью обновляется живьём (через 150 мс после правки) на текущем
    `marked` + DOMPurify.
  - Картинки проекта в `![](img.png)` подставляются как blob-URL.
  - Кнопки Run у `.md` больше нет.
- **PDF.** `pdfjs-dist`, загружается по требованию. Страницы
  рендерятся в canvas по ширине области, листаются прокруткой, есть
  счётчик страниц.
- **PPTX.** `pptx-preview`, рендер в DOM, листание по слайдам. Качество
  ниже PowerPoint. Мы это принимаем, потому что выбрали передачу файлов
  без сервера.
- **Презентация (только admin).**
  - Кнопка «Презентовать» у открытого PDF или PPTX выставляет
    `state.presentation = { path, page, by }`.
  - У всех открывается полноэкранный слой внутри приложения на нужной
    странице.
  - Ведущий листает стрелками, пробелом или кликом. Esc или кнопка
    завершают показ.
  - Остальные не могут ни листать, ни закрыть слой.
  - Если ведущий ушёл, кнопку «Завершить» видит любой admin.

## 6. Веб: HTML, CSS, JS

- **Monaco.** Подключаем встроенные языки `html`, `css` и `javascript`
  с их воркерами. Воркеры поднимаются по требованию, только когда
  открыт такой файл.
- **Проверка.**
  - JS — диагностика TS-воркера: синтаксис и подсказки.
  - CSS — встроенный линт CSS-воркера.
  - HTML — HTMLHint в основном потоке, с задержкой. Результат
    показывается маркерами Monaco, как у Ruff.
- **Run на `.html`** открывает превью на месте консоли, с вкладками
  «Превью | Консоль».
  - Страница загружается в `<iframe sandbox="allow-scripts allow-modals" srcdoc>`.
    Origin у неё непрозрачный, поэтому код ученика не может достать
    данные приложения у учителя.
  - Ссылки на файлы проекта (`<link href>`, `<script src>`, `<img src>`,
    `url()` в CSS) заменяются на `data:`-URL. Внешние `http(s)` остаются
    как есть.
  - Импорты ES-модулей между файлами не поддерживаются.
  - Вывод `console.*` и ошибки страницы приходят через `postMessage` в
    общую консоль. Отражение такое же, как у Python, через `mirrorRun`.
  - Превью видит только тот, кто нажал Run.
- **Run на `.js`** выполняет файл в скрытом sandbox-iframe, вывод идёт в
  консоль.
- **`.css`** ничего не запускает: только проверка и форматирование.

## 7. Форматирование

- Prettier standalone, загружается по требованию, с плагинами `html`,
  `postcss`, `babel`, `estree`, `markdown`. Покрывает `.html`, `.css`,
  `.js` и `.md`.
- Python форматируется Ruff, JSON — как сейчас.
- Кнопка Format доступна для всех этих типов.

## 8. Задания с автопроверкой

- **Файлы.** Тесты к `name.py` лежат рядом в `name.test.py`. Внутри —
  функции `def test_*()` с `assert`.
- **Хелпер `pycode_test`.** `run(stdin="") -> str` запускает решение как
  `__main__` с заданным вводом и возвращает stdout. Если решение упало,
  хелпер бросает исключение.

```python
from pycode_test import run
from task import add

def test_add():
    assert add(2, 3) == 5

def test_io():
    assert run("2\n3\n") == "5\n"
```

- **Кнопка «Проверить»** появляется у `name.py`, если в `structure` есть
  `name.test.py`.
  - Нажатие отправляет сигнал `check {path}` проверяющему: текущему owner,
    если он admin, иначе любому admin онлайн.
  - Если в сети нет ни одного admin, кнопка неактивна с подсказкой «Нужен
    учитель онлайн».
  - Admin и владелец в одиночном режиме проверяют у себя.
- **Проверка у admin.**
  - Каждый раз поднимается новый Pyodide-воркер с пакетами проекта.
  - Решение записывается в FS. Тест в FS не попадает: он выполняется из
    строки, а его модуль удаляется из `sys.modules`.
  - У воркера нет сети, IndexedDB и `caches`.
  - Таймаут — 30 с.
- **Ответ** `check-result {path, results: [{name, ok, message}], error?}`
  приходит только тому, кто запросил. Сообщения обрезаются до 200
  символов. Ученик видит список: зелёные и красные строки в области
  консоли. Результаты нигде не сохраняются.
- **Остаточный риск.** Решение выполняется в одном интерпретаторе с
  тестом. Ученик, который целенаправленно пишет код для извлечения теста
  через интроспекцию и сообщения ошибок, теоретически может его достать.
  Случайный и простой просмотр (DevTools, FS, сеть) защищён.

## 9. Отладчик

- **Запуск.** Кнопка «Отладка» (иконка жука) рядом с Run для `.py`.
- **Точки останова** ставятся кликом по полю слева от номеров строк.
  Они локальные: не синхронизируются и хранятся в `localStorage` для
  каждого пути.
- **Воркер.** Подкласс `bdb.Bdb`, трассируются только файлы проекта. На
  остановке воркер отправляет:
  - `{file, line, stack, locals}`: `repr` каждой переменной до 200
    символов, не больше 50 переменных;
  - пользовательские глобальные переменные.

  Затем воркер ждёт команду через `SharedArrayBuffer` и `Atomics`, как
  при `input()`.
- **Интерфейс.**
  - Панель в шапке консоли: Продолжить (F5), Шаг (F10), Войти (F11),
    Выйти (Shift+F11), Стоп.
  - Текущая строка подсвечивается, её файл открывается.
  - Справа в консоли панель «Переменные / Стек».
- **Сессия.** Исполнитель зеркалирует состояние отладки в
  `runtime.debug`, поэтому все видят строку и переменные. Управляет
  только исполнитель.

## 10. Доска

- **Вкладка** «Доска» стоит между Code и Packages.
- **Библиотека:** `@excalidraw/excalidraw` 0.18 (MIT, React 19),
  загружается по требованию.
  - Тема совпадает с темой приложения.
  - Шрифты и ассеты раздаём сами (`EXCALIDRAW_ASSET_PATH`) из-за COEP.
- **Синхронизация** через документ `board`:
  - элементы: `Y.Map<id, element>`;
  - картинки: `Y.Map<fileId, {mimeType, dataURL}>`.

  Из `onChange` отправляются элементы с выросшей `version`. Удалённые
  изменения применяются через `updateScene`, при конфликте побеждает
  бо́льшая `version`, как устроен reconcile в Excalidraw.
- **Указатели участников:** awareness `boardPointer` с частотой примерно
  20 раз в секунду, передаются в `collaborators`.
- **Права.** `read` или заморозка → `viewModeEnabled`.

## 11. Сервер

- **Postgres.**
  - В `sessions` добавляется `ask_name bool`, `mode` больше не
    используется.
  - Новая таблица `session_codes(code pk, session_id, role, level)`.
  - Старые сессии перестают работать. Они и так истекают через 24 ч.
- **REST.**
  - `POST /api/sessions {askName, roles:[{name,level}]}` создаёт сессию и
    возвращает `{session, codes:[{role,level,code}]}`.
  - `GET /api/sessions/{code}` возвращает `{session(askName), role, level}`.
  - `GET /api/sessions/{code}/codes` возвращает все коды. Доступно owner
    и admin.
  - `POST /api/sessions/{code}/roles {name, level}` создаёт новый код.
    Доступно owner и admin, который сейчас онлайн в комнате.
- **WS.**
  - `peerInfo` получает поле `level`.
  - `welcome` дополнительно содержит `owner`.
  - Новое сообщение `owner {peer}`.
  - `reset` принимается только от текущего `room.owner`.
- Сервер по-прежнему не видит содержимое проекта.

## 12. Этапы

Каждый этап заканчивается рабочим состоянием, которое можно выкатить:

1. **Модель проекта.** Хранилище из нескольких документов, синхронизация
   с `docId`, миграция. Поведение для пользователя не меняется.
2. **Доступ.**
   - уровни, кастомные роли, папки, `protected` и `hidden`;
   - `.pycode.env`;
   - серверные коды и роли, замена владельца;
   - новое окно «Поделиться».
3. **Сессия.** Имена, «Следовать», тумблер подписей, заморозка с
   анимацией.
4. **Файлы.** Бинарные файлы, перетаскивание, лимит, просмотр картинок,
   бинарные файлы в zip.
5. **Просмотр.** Markdown «рядом», PDF, PPTX, презентация.
6. **Веб.** HTML/CSS/JS (языки, проверка, превью, запуск), Prettier.
7. **Обучение.** Автопроверка, отладчик.
8. **Доска.**

## 13. Проверка

- На каждом этапе: `npx tsc -b`, `npx oxlint src`, `go vet` и `go test`
  для бэкенда, пересборка контейнера.
- Сквозные сценарии в puppeteer, в реальном Chrome, с тремя браузерами
  (owner, admin, ученик с кастомной ролью):
  - ученик не получает документы скрытых файлов и чужих папок
    (проверяем загруженные `docId`);
  - запись в защищённый файл от write отбрасывается;
  - заморозка блокирует ввод;
  - замена владельца срабатывает при уходе owner и откатывается при его
    возвращении;
  - бинарный файл доходит до другого браузера, и `sha256` совпадает;
  - презентация синхронно листается;
  - проверка решения возвращает pass и fail;
  - отладчик останавливается на точке останова;
  - доска синхронизируется.
- Go-тесты: выдача кодов и ролей, выбор `room.owner`, отказ `reset` не
  от owner.
