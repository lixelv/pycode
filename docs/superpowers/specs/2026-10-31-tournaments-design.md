# Турниры в проверках polycode

Дата: 2026-10-31. Статус: на проверке.

## Цель

Проверки (`name.test.py`) можно использовать на олимпиаде: у тестов есть баллы, лучший результат каждого участника попадает в общую таблицу, а решение на Python не может подделать результат. Отдельно появляется наследование тестов по папкам, оно работает и вне турниров.

Не входит в задачу: рейтинг по скорости, расписание туров и таймер олимпиады, экспорт таблицы, сброс таблицы из интерфейса (чтобы начать заново, тесты указывают новый id), таблицы в архивах проекта.

## Наследование тестов

Для решения берётся ближайший файл теста с тем же именем: сначала в папке решения, затем в родительских папках, вплоть до корня проекта. Для `a/ivan/tri.py` порядок такой: `a/ivan/tri.test.py`, `a/tri.test.py`, `tri.test.py`.

- `testPathOf(path, files)` получает список файлов проекта и возвращает найденный путь или `null`. Заголовки и сами файлы тестов по-прежнему не имеют тестов.
- Кнопка Check показывается, если тест найден.
- Подменить тест ученик не может: менять дерево файлов могут только администраторы.
- Правило одно для обоих режимов.

## API в файле теста

```python
import polycode_test as t

t.tournament("spring-2026")            # или tournament("spring-2026", private=True)

@t.points(10)
def test_small():
    assert t.run("2\n").strip() == "4", "неверный ответ"

@t.points(30)
def test_big():
    assert t.run("1000000\n", timeout=2).strip() == "..."
```

### `tournament(id, private=False)`

- `id` — непустая строка до 64 символов. `private=True` закрывает таблицу от учеников.
- Вызов должен быть отдельной инструкцией верхнего уровня файла. `run_tests` находит его разбором `ast` **до выполнения** файла (имя `tournament` или атрибут `.tournament`). Файл с таким вызовом целиком турнирный, включая тесты выше вызова.
- Вызов не на верхнем уровне и второй вызов в файле становятся ошибкой файла теста (результат `tests`, как при синтаксической ошибке).
- Неверные аргументы — тоже ошибка файла теста.

### `points(amount)`

- Декоратор возвращает ту же функцию и записывает её стоимость, поэтому поиск `test_*` не меняется. `amount` — положительное конечное число, иначе ошибка файла теста.
- Тест без `@points` стоит 0 баллов. Его падение тоже останавливает запуск.
- Вне турнира декоратор ни на что не влияет.

### Выполнение

- Тесты идут в порядке объявления.
- В турнире после первого упавшего теста остальные не запускаются и приходят с `skipped: true`.
- Вне турнира, как сейчас, запускаются все тесты.

Подсказки: `tournament` и `points` добавляются в `python/stubs/polycode_test.py`, а `tests/test_stub.py` проверяет их наличие и совпадение параметров с `checker.py`.

## Изоляция

В турнире код решения не выполняется в интерпретаторе тестов.

- **Интерпретатор тестов** не получает файлы проекта: они не записываются на диск и не попадают в `sys.path`. Иначе файл ученика `random.py` подменил бы `import random` в тесте. Пакеты из импортов теста загружаются до отключения сети, как сейчас.
- **`run()`** работает по пути C++: блокирующий вызов через страницу с результатом в `SharedArrayBuffer` (`BATCH_*`). Обобщается существующий путь `_run_cpp` → `_run_wasm` → `polycode_run_wasm`.
- **Воркер решения:** новый `RunnerClient` на проверку с запросом одиночного запуска. В нём есть проект (`projectFiles`) и пакеты проекта, но нет сети, IndexedDB и кэшей, как в обычной проверке. Решение выполняется как `__main__`, модули проекта импортируются заново на каждый запуск. После превышения времени воркер уничтожается и создаётся новый.
- **Поведение `run()` в Python-турнире:**
  - подсказки `input()` не входят в вывод, как в обычной проверке Python;
  - чтение после конца `stdin` даёт `EOFError` в решении, то есть `exit code 1`, если решение его не обработало;
  - ненулевой выход и необработанное исключение — `ExitCodeError`; превышение лимита вывода и незапуск — те же ошибки, что у C++.
- **Время:** отсчёт и `timeout` начинаются, когда воркер решения готов; запуск Pyodide в лимит теста не входит.
- **`polycode_test.module`** в турнире вызывает `TypeError`.
- **Общий лимит** турнирной проверки — 120 с вместо 30, и для Python, и для C++ (константа и параметр `check`).

C++ уже выполняется отдельно; для него добавляется только запрет файлов проекта в интерпретаторе тестов.

## Таблица

### Данные

- `structure.tournaments`: `id → {private: boolean}`. Записывается администратором при первой проверке и при смене флага.
- Документ `t:<id>`: `Y.Map` `results`, ключ `<userId>/<задача>`, значение `TournamentEntry`:

```ts
interface TournamentEntry {
  name: string       // имя участника на момент записи
  score: number
  max: number        // сумма баллов всех тестов файла в этом запуске
  passed: string[]   // имена пройденных тестов
  at: number         // Date.now() администратора
}
```

- Участник — публичный id с сервера (`identity.Public`, поле ссылки), не из сообщения ученика.
- Задача — имя файла теста без `.test.py`, то есть `tri`. Личный `ivan/tri.test.py` и общий `tri.test.py` дают одну колонку.

### Доступ

- `docAccess`: `t:<id>` — запись только администраторам. Чтение: всем, если турнир открыт; для `private` ученик получает `none`. Правила берутся из `structure` через `Rules.tournaments`.
- Закрытая таблица не уходит ученикам благодаря существующей рассылке документов только тем, кто может их читать. Результат своей проверки ученик всё равно видит на вкладке Tests.
- `ProjectStore` открывает документы `t:<id>` по `structure.tournaments`. `replaceProject` и Reset их удаляют. В архивы таблицы не попадают.

### Подсчёт

Так как запуск останавливается на первом падении, пройденные тесты всегда идут с начала файла подряд, и лучший запуск — тот, что дошёл дальше всех.

- Новая запись заменяет старую, только если `score` строго больше. Равный результат не меняет `at`.
- Если учитель изменил тесты, старые записи остаются до нового лучшего результата. Чтобы начать заново, тесты указывают новый id.

### Места

Сумма `score` по задачам, по убыванию. При равенстве выше тот, у кого раньше максимальный `at` по его задачам. Логика в чистом модуле `lib/tournament.ts` (`recordRun`, `standings`).

## Что идёт в зачёт

Запись делает `App.tsx` у администратора, который выполнил проверку, и только если соблюдены все условия:

1. В сессии: проверку запросил ученик сигналом `check` (`from` уже подтверждён сервером). Собственная проверка администратора показывает результат, но не записывается.
2. Без сессии: результат записывается локально под своим id, чтобы турнир можно было опробовать.
3. `fileAccess(ученик, решение) === "write"`.
4. `fileAccess(ученик, файл теста) !== "write"`.

Если условия 3 или 4 не выполнены, ученик получает результаты тестов и сообщение, что в таблицу они не записаны.

## Результаты и интерфейс

- `CheckResult` получает `skipped?: boolean` и `points?: number`.
- Результат проверки дополняется `tournament?: {id, private, max}`. Сигнал `check-result` передаёт те же поля.
- Вкладка Tests: пропущенные тесты серым со словом «пропущен», стоимость теста, итог «N из M баллов» в турнире.
- Новая вкладка нижней панели «Турнир» показывается, если есть турнир, таблицу которого можно читать: место, имя, баллы по задачам, сумма. Если турниров несколько — выбор сверху. Обновляется живьём из документа.
- Все строки через `t()`, на EN и RU.

## Обработка ошибок

- Ошибка файла теста (синтаксис, неверный `tournament` или `points`) — одна строка `tests`, в таблицу ничего не пишется.
- Не скомпилировалось решение C++ или вышел общий лимит: сообщение как сейчас, в таблицу ничего не пишется.
- Воркер решения не загрузился: `ProgramNotStarted`, тест падает с `the program did not start`.
- Сообщения для ученика строятся по существующим правилам `_failure`: вывод решения в них не попадает.

## Известные ограничения

- Проверки идут по одной в браузере одного администратора, с паузой 3 с на ученика. При многих участниках и длинных тестах очередь станет заметной.
- Таблица живёт у владельца. Результаты теряются, если владелец вышел, а замещающий администратор ушёл до его возвращения, а также при очистке данных браузера владельца.
- Если решение лежит в файле, который могут менять несколько учеников, один может присвоить чужой код. Каждому участнику нужна своя папка с ролью.
- Память в Python-турнире измеряется `tracemalloc` внутри интерпретатора решения, и программа может исказить этот замер. Время измеряется снаружи, вывод передаётся как есть.
- Время зависит от компьютера администратора, поэтому лимиты задаются с запасом.
- Места при равенстве зависят от часов администратора.

## Тестирование

- `tests/test_checker.py`: определение турнирного файла, ошибки `tournament` и `points`, порядок, остановка на падении и `skipped`, отсутствие остановки в обычном режиме, `module` даёт `TypeError`, файлы проекта не попадают в `sys.path`, `run()` идёт через хук.
- `tests/test_stub.py`: новые имена и параметры.
- vitest: `testPathOf` (ближайший файл, родители, корень, файл теста, заголовок), `docAccess` для `t:` (открытый, закрытый, запись), `recordRun`, `standings` с равенством.
- Chrome (puppeteer-core), реальная сессия с учителем и двумя учениками:
  - наследование теста и приоритет более близкого файла;
  - баллы, пропущенные тесты, лучший запуск сохраняется после худшего;
  - таблица живьём у всех, закрытая таблица недоступна ученику;
  - решение Python, которое через `sys.modules` и `gc` пытается подделать результат, не получает баллов;
  - решение с `random.py` в проекте не меняет `import random` в тесте;
  - турнирная проверка C++;
  - обычные проверки работают как раньше.
