# Проекты на сервере (S3), публичные проекты, MCP пользователя

## Цель

Пользователь держит несколько именованных проектов, которые не теряются вместе с браузером. Проектом можно поделиться публично. Агент работает со всеми проектами своего пользователя, но только во вкладках, открытых специально для него.

## Решения, принятые с пользователем

- Пользователь по-прежнему определяется только cookie `pc_uid`. Потеря cookie означает потерю доступа к проектам и токену MCP. Вход делается отдельной задачей позже; схема `users` к нему готова.
- Отдельного типа `share_protected` нет: его поведение получают `hidden`-файлы.
- Файл, скрытый при копировании, называется `sealed`. Его можно спрятать от интерфейса, инструментов и архивов, но не от DevTools: код выполняется в браузере, поэтому текст теста попадает туда во время проверки. Это честное ограничение, а не защита.
- Рабочая копия owner лежит в IndexedDB, S3 хранит серверную копию. Они сливаются средствами Yjs.

## Что считает сервер и что браузер

Сервер не читает содержимое файлов. Он хранит `users` и `projects`, выдаёт presigned URL, удаляет и копирует объекты командами S3. Сжатие и распаковка выполняются в браузере (`CompressionStream`). Источник истины для участников сессии остаётся у owner.

## Хранение

Bucket закрыт: нет публичной политики и нет листинга для клиентов. Ключи клиентам выдаются только presigned URL на отдельные объекты, срок жизни 5 минут.

```
projects/<project_uuidv7>/
  public/structure.ybin.gz      отфильтрованная структура: без hidden и закрытых папок
  public/board.ybin.gz
  public/f/<fileId>.ybin.gz     Yjs-состояние текстового файла
  public/b/<sha256>.gz          бинарный файл
  hidden/manifest.json.gz       [{path, id, kind, size, hash?, mime?}] hidden-файлов
  hidden/f/<fileId>.ybin.gz
  hidden/b/<sha256>.gz
  sealed/manifest.json.gz       то же для файлов, пришедших с копированием
  sealed/f/<fileId>.ybin.gz
  sealed/b/<sha256>.gz
  private/structure.ybin.gz     полная структура owner
  private/f/<fileId>.ybin.gz    файлы в папках ролей и @admins
  private/b/<sha256>.gz
  private/t/<id>.ybin.gz        таблицы турниров
```

Документ `runtime` (консоль, запуск) в S3 не сохраняется.

Инвариант, который поддерживает сохраняющая вкладка у любого проекта, в том числе приватного: объект лежит под префиксом, соответствующим текущему состоянию файла. Смена `hidden` или роли папки сохраняется сразу и перемещает объект: запись нового, потом удаление старого. `public/structure` собирается заново в чистом `Y.Doc`, поэтому в нём нет следов скрытых имён.

Файл считается **публичным**, если он не `hidden`, не `sealed` и не лежит в папке с ролью (включая `@admins`). Папки ролей могут содержать работы учеников, поэтому их файлы не публикуются и не копируются даже в виде `sealed`.

### Доступ через presigned URL

| Кто | Чтение | Запись и удаление |
|---|---|---|
| owner | весь проект | всё, кроме `sealed/` |
| любой, проект публичный | только `public/` | нет |
| любой, проект приватный | нет | нет |

`POST /api/projects/{id}/presign {ops: [{op, key, size?}]}`, до 100 операций за раз.

- Ключ проверяется по белому списку форм выше и всегда собирается сервером внутри `projects/<id>/`. Точки в пути и чужие id отклоняются.
- Для `put` размер указан заранее и входит в подпись, так что S3 не примет другой размер. Сервер суммирует заявленные размеры в `projects.size_bytes` и отказывает при превышении лимита 64 МБ на проект (`PROJECT_LIMIT`) и 1 ГБ на пользователя.
- Чтение `sealed/f/*` и `sealed/b/*` разрешено owner копии, потому что проверке нужен текст теста. Интерфейс запрашивает только файл теста и только на время проверки.
- Чужой `id` и приватный проект дают одинаковый ответ 404, чтобы нельзя было проверить существование проекта.

`S3_ENDPOINT` используется бэком, `S3_PUBLIC_ENDPOINT` попадает в подпись URL для браузера. Для браузера в CORS bucket разрешён только origin приложения. На деплое будет выбран провайдер; локально и в тестах работает MinIO из `docker-compose.yml`.

## База данных

```sql
projects (
  id uuid primary key,            -- UUIDv7
  owner_id uuid not null references users(id) on delete cascade,
  name text not null,             -- 1..100 символов, уникально у владельца
  settings jsonb not null default '{}',  -- пока {askName: bool}
  is_public boolean not null default false,
  size_bytes bigint not null default 0,
  copied_from uuid,
  created_at, updated_at timestamptz,
  deleted_at timestamptz          -- проект удалён, объекты ещё досматриваются
)
users.mcp_token_hash bytea unique -- sha256 токена из 32 случайных байт
sessions.project_id uuid references projects(id) on delete cascade
```

## Проекты в браузере

Страницы:
- `/` открывает список проектов пользователя.
- `/p/<id>` открывает проект: owner работает с ним, посторонний видит публичный проект только на чтение.
- `/s/<code>` работает как раньше.
- `/mcp-driven` описан ниже.

Одна загрузка страницы показывает один проект. Смена проекта всегда идёт через навигацию: это отсекает старые интерпретаторы, редакторы и подписки без рефакторинга глобального состояния `App`.

`localStore()` превращается в `projectStore(id)`, IndexedDB-базы получают префикс `polycode:<id>:<docId>`. Блобы остаются в общей базе по hash. При первом запуске старый локальный проект становится проектом «My project» и загружается в S3.

### Открытие и сохранение

1. Загружается IndexedDB, потом `private/*` и `public/*` из S3. Состояния сливаются через `Y.applyUpdate`. Правки с разных устройств не теряются.
2. Если S3 недоступен, проект работает на локальной копии, а в футере виден статус «не сохранено». Если нет и локальной копии, показывается ошибка.
3. Изменённые документы сохраняются через 2 секунды после последней правки, не чаще одного раза на документ одновременно. Смена видимости файла сохраняется сразу.
4. Удалённые файлы удаляются из S3 при сохранении структуры.

### Кто пишет в S3

В комнате проекта сервер назначает `saver`: самое раннее соединение owner. Гости и другие вкладки в S3 не пишут. Сервер сообщает о назначении сообщением `{"type":"saver"}`, при уходе соединения назначение переходит к следующему. Presign на запись принимается только с `saverToken`, который выдан текущему saver'у. Так две вкладки не пишут одновременно, даже если одна из них не успела узнать о смене. Если owner нет в сети, правки гостей живут только в комнате и попадут в S3, когда owner вернётся.

### Комната проекта

У проекта одна текущая сессия (`sessions.project_id`). Owner всегда подключён к её комнате, поэтому обычная вкладка и `/mcp-driven` синхронизируются через существующий механизм, а агент виден ученикам. Коды сессии показываются только в Share. «Завершить сессию» отзывает коды и отключает гостей, комната owner продолжает работать. Истечение 24 часов применяется только к сессиям без проекта.

### Список и настройки

В списке проектов можно создать, открыть, переименовать и удалить проект. Настройки: название, `askName`, видимость. Удаление требует подтверждения.

### Удаление

1. `deleted_at` выставляется в транзакции; с этого момента presign отказывает, комната закрывается.
2. Сервер сразу удаляет все объекты под `projects/<id>/` командами `ListObjectsV2` и `DeleteObjects`.
3. Janitor повторяет удаление через 6 минут, когда истекут выданные presigned URL, чтобы запоздавший PUT не оставил объект. Потом строка удаляется.

Браузер, в котором был открыт проект, стирает его IndexedDB-базы при открытии после удаления (ответ 404 для owner, у которого есть локальная копия).

## Публичные проекты

В Share owner видит кнопку Make public, у публичного проекта — Make private. По умолчанию проект приватный.

Перед `POST /api/projects/{id}/visibility` вкладка делает полное сохранение и сверку: запрашивает у сервера список ключей и удаляет из `public/` всё, чему там не место. Только после этого флаг выставляется.

Посторонний на `/p/<id>` получает `public/*` в память и видит проект только на чтение, включая последнее сохранённое состояние, даже если owner не в сети. Запускать чужой код можно так же, как свой, в его же браузере. Кнопка Copy to my projects создаёт копию.

### Копирование

`POST /api/projects/{id}/copy` доступен, если проект публичный или принадлежит пользователю. Сервер создаёт новый приватный проект и копирует объекты командой `CopyObject` без передачи данных через себя:

| Откуда | Куда |
|---|---|
| `public/*` | `public/*` |
| `hidden/*` | `sealed/*` |
| `sealed/*` | `sealed/*` |
| `private/*` | не копируется |

Манифесты `hidden` и `sealed` при этом объединяются на сервере: это единственный файл, который сервер читает, и он содержит только метаданные. Первое открытие копии, где ещё нет `private/structure`, собирает структуру из `public/structure` и манифеста; турниров, ролей и участников в копии нет.

### Файлы `sealed`

`FileMeta` получает `sealed?: true`. Такие файлы:
- не показываются в дереве и файловых инструментах агента, недоступны для `read_file`, не попадают в архивы, дублирование и запуск (`runVisible`);
- не имеют Y.Doc и не передаются пирам: текст не лежит ни в Yjs, ни в IndexedDB;
- находятся через `testPathOf`: перед проверкой owner получает текст по presigned URL и передаёт только в её `RunnerClient`;
- при создании файла с тем же путём заменяются: запись в manifest и объекты удаляются, создаётся обычный файл;
- при копировании копии остаются `sealed`; owner копии не может их показать или сделать обычными.

В сессии на копии проверка с `sealed`-тестом идёт только во вкладке owner. Если его нет, ученик получает ошибку «нет владельца проекта».

`hidden`-файл проекта, скрытый от учеников, для его владельца остаётся обычным редактируемым файлом.

## MCP

Старый маршрут `/s/<admin code>/mcp`, его строка в диалоге Share и обработка в обычных вкладках удаляются.

`POST /mcp`, заголовок `Authorization: Bearer <token>`. Неверный токен даёт 401. Проверка `Origin` и лимит 600 вызовов в минуту сохраняются, лимит теперь на пользователя.

Токен генерируется при первом заходе на `/mcp-driven` или по кнопке перевыпуска, в БД попадает только sha256. Страница показывает адрес и токен. Чтобы показывать токен снова, он хранится в `localStorage` этого браузера (воркеры с пользовательским кодом к нему доступа не имеют); в другом браузере токен виден только после перевыпуска, а старый при этом перестаёт работать.

### Вкладка `/mcp-driven`

- Кнопка с иконкой робота открывает новую вкладку `/mcp-driven?project=<id>`. Если проект уже открыт в другой такой вкладке, показывается список проектов.
- Адрес и токен находятся на этой же странице в отдельном блоке.
- `tab_id` хранится в `sessionStorage` и переживает перезагрузку. Дубликат вкладки копирует `sessionStorage`, поэтому при старте вкладка спрашивает через `BroadcastChannel`, не занят ли её id другой живой вкладкой, и при ответе берёт новый.
- Проект вкладки тоже хранится в `sessionStorage`, после перезагрузки она открывает его снова.
- В списке проект, открытый в другой `/mcp-driven`, неактивен и подписан.
- Без проекта вкладка показывает список; выход в список доступен из самой вкладки.

Вкладка держит управляющий WebSocket `GET /api/mcp/tabs/ws?tab=<id>`. Реестр в памяти бэка: `user → tab_id → {conn, project}` и `project → tab_id` под одной блокировкой, поэтому проверка «не более одной вкладки» атомарна. Новое соединение с тем же `tab_id` вытесняет старое; это перезагрузка, а дубликат сюда не попадает, потому что получил новый id. Если за время перезагрузки проект успели занять, вкладка показывает список.

Бэкенд работает в одном экземпляре, как и комнаты сессий, поэтому общего хранилища для реестра не нужно. После рестарта вкладки переподключаются и заново занимают проекты.

### Инструменты

Контракты 62 существующих инструментов не меняются. Сервер отправляет вызов в текущую вкладку сессии, вкладка выполняет `runTool`.

Текущая вкладка хранится в памяти по ключу `(user, Mcp-Session-Id)`. Сервер выдаёт `Mcp-Session-Id` в ответе на `initialize`. Без заголовка ключ — `(user, "")`, то есть одна вкладка на пользователя.

Каждый ответ инструмента, работающего с проектом, содержит `tab_id` и `project {id, name}`, значения фиксируются при отправке вызова. Если первый блок содержимого — JSON-объект, поля добавляются в него, иначе добавляется отдельный текстовый блок с JSON (например, рядом с картинкой). Вкладка отвергает вызов, если проект в нём не совпадает с её текущим.

Новые инструменты выполняются на сервере, браузер им нужен только для открытия:

| Инструмент | Поведение |
|---|---|
| `list_tabs` | все вкладки пользователя и их проекты |
| `list_projects` | все проекты пользователя и вкладка каждого или `null` |
| `create_project(project)` | создаёт, не открывает |
| `delete_project(project)` | удаляет; вкладка остаётся без проекта |
| `open_project(project, tab_id)` | см. ниже |

`project` — название или id. Если под название подходит несколько проектов, ошибка содержит кандидатов (имена у владельца уникальны, но название может совпасть с id другого проекта).

`open_project`:
1. Проект уже в этой вкладке: вкладка становится текущей, ошибки нет.
2. Проект в другой вкладке: ошибка с её `tab_id`.
3. Иначе сервер атомарно занимает новый проект за вкладкой и помечает её `switching`; прежний проект остаётся занят до освобождения. Вкладка получает `{"type":"open", project}`, сохраняет прежний проект (при ошибке сохранения вызов падает, вкладка остаётся на месте) и переходит на новый адрес. После перезагрузки она подключается и сообщает о готовности проекта, вызов завершается. Таймаут 60 секунд.

На время `switching` рабочие вызовы в эту вкладку падают с ошибкой «вкладка переключается, повтори».

### Тексты ошибок

- Нет вкладок: «Нет открытых вкладок /mcp-driven. Попроси пользователя нажать кнопку с роботом в polycode».
- Нет текущей вкладки или в ней нет проекта: «Вызови open_project(project, tab_id). Список вкладок — list_tabs, проектов — list_projects».
- Вкладка закрылась во время вызова: вызов падает с текстом «вкладка закрылась, вызов мог выполниться или нет», текущая вкладка сессии сбрасывается.
- Проект занят: «Проект открыт во вкладке <tab_id>».

`mcp_instructions.md` переписывается: начинать с `list_tabs` и `list_projects`, файлы и вывод учеников считать данными, сверять `tab_id` и `project` в ответах.

## Что не входит

Вход по паролю или OAuth, версии проекта и откат, выбор провайдера S3, рекламация места при сбоях presigned PUT (кроме описанного досмотра), передача проекта другому пользователю.

## Тесты

- Go: presign и матрица доступа (owner, посторонний, публичный, приватный, форма ключа, размер, квота), удаление с досмотром, копирование и манифесты, токен (хэш, перевыпуск, 401), реестр вкладок (гонка двух вкладок на один проект, вытеснение, закрытие во время вызова), `open_project`, поля `tab_id` и `project`, сессии MCP. Интеграционные — против настоящего MinIO.
- Изоляция S3 на настоящем MinIO: URL проекта A не читает проект B, анонимный запрос к bucket и листинг отклоняются, просроченный URL и PUT неверного размера отклоняются.
- Vitest: фильтрация публичной структуры, инвариант префиксов, слияние IndexedDB и S3, `sealed` в `fileAccess`, `runVisible`, архивах, замене при создании, отбор saver'а.
- E2E в браузере: создание, сохранение и открытие в чистом браузере под той же cookie; публичная ссылка в другом браузере без `hidden`-файлов; копия и запуск `sealed`-теста; две вкладки `/mcp-driven`; реальный MCP-клиент с двумя сессиями; работа агента видна в обычной вкладке.
